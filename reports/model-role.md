# DeepSeek 在第一次成功实验中实际做了什么

**它是一个依赖观察反馈、持续选择目标位姿的任务策略层：选对象、选测量点、决定抓取朝向和偏移、给出移动目标，并按反馈纠偏。** 现成代码负责感知测量、姿态数学、IK、轨迹与低层控制。它既不是只说“开抽屉”，也没有自己写控制器。

最有区分力的证据是：**Contact-GraspNet 没返回任何抓姿，后续成功用到的抓取方向和目标位置，仍由模型显式填入。**

分析对象：原始成功 run `ora-interactive-libero-d8c68723d9b8--20261107T014312Z`。审计其 16 次 API 回复、16 次工具调用、7 个世界动作及 498 个控制步；不重新运行模型或模拟器。以下坐标均为世界坐标，单位 m。

## 1. 从模型输出到实际动作，有完整数值链

### 选目标，而不是接受工具首选

模型第一次查询的是 `drawer handle of the dark cabinet`，相机为 `agentview`，最多 3 个候选。它选择了中层把手的 `target_ref`，而不是工具最高分的 T0 候选，随后调用 `grasp_plan`。

抓取工具返回 `status=no_candidate`、`candidates=[]`，生成和检查的抓姿数量都为 0。因此，本次轨迹没有采用任何 Contact-GraspNet 生成的抓姿。

### 决定接近方向、抓取朝向和 13 cm 偏移

模型指定图像像素 `[78,157]` 请求深度反投影，工具返回把手坐标：

```text
[0.0573433, -0.1353014, 1.0239317]
```

模型舍入后给出：

```python
handle = [0.05734, -0.13530, 1.02393]
pregrasp = handle + np.array([0.0, 0.13, 0.0])
```

`compute` 只执行加法，返回 `[0.05734,-0.0053,1.02393]`。下一轮模型把这个值原样交给 `move_pose`，并明确指定：

```json
{
  "position_m": [0.05734, -0.0053, 1.02393],
  "approach_world": [0, -1, 0],
  "jaw_line_world": [0, 0, 1],
  "interaction": "free_space"
}
```

上面是调用的关键字段节选，完整参数见逐轮输出。**选择 +y 方向的前置位置、13 cm 距离、−y 接近轴和 +z 夹爪轴，都是模型的决策。** 工具将轴向编译成四元数 `[0.5,-0.5,0.5,0.5]`，再求解和执行运动。

数值链对应原始 `agent-events.jsonl` 第 17→41→43→46 行：测量→模型提供算式→计算结果→动作参数。

### 根据新图像重新居中，不是一次性照抄坐标

靠近后，模型在腕相机中标记把手两端和中部：`[140,125]`、`[140,205]`、`[140,165]`。

工具测得两端 x 为 `0.0051764`、`0.0620590`，均值 `0.0336177`。模型可见文字明确说当前抓取点靠近把手一端，应重新居中；下一目标变为：

```text
[0.03362, -0.128, 1.0152]
```

目标 x 从 `0.05734` 改为 `0.03362`，即向把手中心修正 23.72 mm；目标 z 也更新。x/z 与新测量的端点中心舍入相符，y 由模型另向内深入约 3.71 mm。这一步没有额外 `compute` 调用替模型生成目标。

原始证据：第 64→66→70 行，像素选择→测量→模型的新目标。

### 选择闭爪时机，并分三段拉动

| 世界动作 | 模型给的目标/指令 | 实际执行 |
|---|---|---|
| 1 前置姿态 | `[0.05734,-0.0053,1.02393]`，接近轴 −y、夹爪轴 +z | 到位，364 控制步 |
| 2 接近 | `[0.05734,-0.105,1.02393]` | 实际沿 −y 约 97.67 mm，33 步 |
| 3 居中并深入 | `[0.03362,-0.128,1.0152]` | 实际 Δxyz 约 `[-23.23,-23.87,-8.36]` mm，29 步 |
| 4 闭爪 | `close` | 12 步后爪停在约 17.36 mm 开口 |
| 5 试拉 | `[0.0341,-0.0766,1.0156]` | 实际 +y 45.64 mm，19 步 |
| 6 继续拉 | `[0.0341,0,1.016]` | 实际 +y 77.12 mm，31 步 |
| 7 再拉 | `[0.0341,0.05,1.016]` | 实际 +y 17.50 mm，10 步时首次触发官方成功 |

模型根据夹爪开口、图像和位移反馈选择继续拉动。诸如“没滑脱”的表述是模型对反馈的解释；官方任务成功来自环境判定。

**最后一步不是多余动作。** 前一步结束时环境仍是 running；第 7 个动作部分执行后首次成功终止。最终 y 只到 `0.0136694`，没有到模型请求的 `0.05`，剩余约 3.63 cm 没有继续执行。之后的 `check_task` 和 `finish_episode` 是确认和收尾，不是它们把任务变成成功。

## 2. 哪些信息被用上，哪些没有进入控制

| 模型输出 | 实际消费方式 | 应如何评价 |
|---|---|---|
| 工具名、相机、查询文字、像素点、目标引用 | 决定调用哪个感知/几何工具、测哪个对象或位置 | 实际采用的主动感知决策；不是机器臂动作本身 |
| 目标 XYZ、接近轴、夹爪轴、开闭指令 | 经编译、Supervisor 和控制器执行 | 直接决定动作的策略信息 |
| 可见解释文字 `content` | 显示、记录，并回填后继模型上下文；命令解析器不读它 | 不直接执行，但不能称完全没用 |
| `reasoning_content` | 不进入机器人命令；通过 provider continuation 回传后继 DeepSeek 请求 | 是模型侧上下文，不是运动代码 |
| 闭爪调用的 `target_ref` | 从动作参数中拆出，只作为 `agent_annotation_only` 记录 | **不控制抓哪个物体**；不会自动对准该引用所指对象 |
| `compute.bindings[].from` | 记录数值来源说明；数学运算使用 `value` | 来源标签，不参与坐标计算 |
| `finish_episode.reason` | 记录模型的结束说明 | 不影响已经产生的官方成功判定 |
| 最后移动目标未执行的余程 | 环境成功后被停止 | 确实没有执行，但该动作已执行的部分促成首次成功 |

闭爪注记的代码会[明确剥离 target_ref](https://github.com/hao-ai-lab/ORA/blob/4d7a26f7c52a18a9f1af292e967aa8b7a526ac61/ora/agent/tools/gripper_intent.py#L24-L48)，再送动作编译器；来源标签的[数值与 provenance 分开处理](https://github.com/hao-ai-lab/ORA/blob/4d7a26f7c52a18a9f1af292e967aa8b7a526ac61/ora/agent/tools/compute_arguments.py#L193-L213)。

### 探测被执行，不代表每个结果都转化成动作

- 第二批 8 个几何测量点，没有可识别的逐坐标复制进入后续命令。但模型文字提到用柜体与把手的 y 关系判断 +y 为打开方向，不能把整次查询判为无用。
- 腕相机 grounding 的 3 个目标引用和工具给的 overhead pose，都没有进入后续结构化调用。模型仍把看到的横杆形状作为朝向线索。
- `grasp_plan` 没产出可执行抓姿，但它的空返回促成了切换到手工几何参数的分支。

### 长推理输出不是“全部被执行”，也不是“全部被丢弃”

本次 API 报告 49,328 个输出 tokens，其中 47,247 个为 reasoning（95.78%）。机器人命令解析器只读 `tool_calls` 的工具名和 JSON 参数，不解析 prose 或 reasoning。

但实际归档的第 3 个请求中，前两轮的 content、reasoning、tool_calls 都原样回传给 DeepSeek。这已按字段直接核实，不是只看配置推断。因此，这些文字有后继模型上下文的消费路径；现有记录无法给其中每段推理分配“必要/浪费”的因果比例。

## 3. 工具自动完成的部分很重

模型没有输出关节轨迹、力矩、每 tick 控制量，也没有改写控制器。现成代码自动完成：

- 从模型选中的像素与 RGB-D 计算世界坐标；
- 将模型指定的轴向换成四元数；
- 5 次 `move_to` 自动保持当前朝向、保留夹爪状态，并选定单臂 wrapper；
- 本次 6 次移动的 cuRobo global joint-position 规划，以及闭爪的局部 OSC 控制；
- 执行中测误差、记录反馈，并在官方成功边界停止。

例如，[move_to 的固定解释](https://github.com/hao-ai-lab/ORA/blob/4d7a26f7c52a18a9f1af292e967aa8b7a526ac61/ora/agent/tools/runtime/move_pose.py#L318-L358)就是绝对 XYZ 加保持当前朝向，并不要求模型重复输出四元数。[执行调用提取器](https://github.com/hao-ai-lab/ORA/blob/4d7a26f7c52a18a9f1af292e967aa8b7a526ac61/ora/agent/native/provider_reply.py#L80-L84)也只提取工具调用，不把自然语言当策略程序运行。

## 结论：模型提供了什么不可混淆的角色

本回合中，DeepSeek 提供的是**视觉目标选择、几何关系判断、稀疏位姿与动作顺序，以及利用反馈的重新定位/继续动作**。它比“调用一个开抽屉技能”具体得多；准确的三维测量、IK、密集运动规划与控制则由强工具栈提供。

这一轨迹能定位模型与代码的实际分工。它尚未比较专门手写的视觉启发式策略，所以不能据此判断这些决策必须由大模型完成。
